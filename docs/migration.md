# Migrating between major versions

Each section lists what a consumer of `buncargo` has to change when crossing one major version, newest first. Breaking changes that shipped inside a minor release are listed under the major you cross when you pick them up. If you are several majors behind, work through the sections from the bottom up.

## 15.x → 16.0

- **`buncargo` is the entry a config imports; the rest moved to `buncargo/api`.** The root exports `defineDevConfig`, `service`, `mergeConfigs`, `discoverApps`, `exists`, `getWorktreeProjectSuffix` and the config types, and loads in a few milliseconds. Import everything else the root exported from `buncargo/api`: `createDevEnvironment`, `loadDevEnv`, `clearDevEnvCache`, `runCli`, `resolveConfig`, `resolveServices`, `validateConfig`, `assertValidConfig`, `runWorkspaceTypecheck`, `getEnvVar`, `isPortInUse`, `killPortOwner`, `getProcessOnPort`, `isProcessAlive`, `waitForServer`, `getLocalIp`, `isCI`, `checkoutProjectNames` and the other project-name helpers, the container runtime, Compose, tunnel and watchdog helpers, and the environment's types (`DevEnvironment`, `AnyDevEnvironment`, `DevEnvironmentFor`, `StartOptions`, `StopOptions`, `WithServicesOptions`, `ServicesStarted`, `CliOptions`, `ResolvedApp`, `ResolvedService`, `PrismaRunner`, `SeedOutcome` and their option types). A `vite.config.ts` that reads `getEnvVar` imports it from `buncargo/api`. `buncargoVite` is no longer on the root: import it from `buncargo/vite`.
- **Ten subpaths are published:** `buncargo`, `buncargo/api`, `/vite`, `/next`, `/client`, `/runtime`, `/expo`, `/shopify`, `/supabase` and `/firebase`. The rest are gone. `buncargo/docker`: import `DockerUnavailableError` and `assertDockerRunning` from `buncargo/api`. `buncargo/config`: the config helpers from `buncargo`, the resolver and validator from `buncargo/api`. `buncargo/types`: from `buncargo`, or `buncargo/api` for the environment's types. `buncargo/environment`, `buncargo/loader`, `buncargo/cli`, `buncargo/typecheck`, `buncargo/container-runtime`, `buncargo/docker-compose`, `buncargo/core/ports`, `buncargo/core/network`, `buncargo/core/process`, `buncargo/core/watchdog`, `buncargo/core/tunnel` and `buncargo/core/utils`: what the root used to export from them is in `buncargo/api`; the rest is internal, as is all of `buncargo/apple-container`.
- **Bun runs the built package.** The `bun` export conditions are gone and the package no longer ships `src/`, so a config loaded by the CLI imports the same build the CLI runs, and one process holds one copy of buncargo. Stack traces still name the source files; the source maps no longer carry the source text.
- **Integration names are typed through `integrations`.** `IntegrationAppNames` is gone. An integration declares the apps and services it adds in its return type, `BuncargoIntegration<{ apps: "stripeListen"; services: "stripeMock" }>`, and `defineDevConfig` accepts those names in `requiredServices`, `requiredApps`, `startAfter`, `tasks` and `profiles` only when the integration is in the config's `integrations`. Replace a `declare module "buncargo" { interface IntegrationAppNames { … } }` with that return type. The built-ins declare theirs: `supabase()` its services, plus `supabaseFunctions` with `functions: true`; `firebase()` the `firebase` app; `shopify()` the `shopify` app.
- **`defineDevConfig` has one signature.** A wrong app or service name is one line (`Type '"web"' is not assignable to type '"api"'`) instead of a "No overload matches this call" over both overloads. A config without `apps` now checks `profiles` and task `app` names too, so a profile naming an app that does not exist fails to compile. The type parameters are now `<TServices, TEnv, TIntegrations, TApps>`; they were never meant to be passed, and passing them is still an error.
- **The config's own `env` wins over Shopify's.** `shopify()` put `SHOPIFY_APP_CONFIG`, `SHOPIFY_API_KEY` and `SHOPIFY_DEV_STORE` over the same keys in the config's `env`; now the config's values win, as they already did over Supabase and Firebase. A config that set one of them by mistake now overrides Shopify's. An app's `staticEnv` now wins over an integration's `appEnv` too (Expo's `RCT_METRO_PORT`, Firebase's `TMPDIR`), as its `envVars` already did.
- **`checks` is `setupChecks`**, in `dev.config.ts` and on `BuncargoIntegration`, so setup checks are no longer one letter from `check` (the gates). Validation names the replacement.
- **A service's preset is its only identity.** A raw `docker` definition under a preset's key (`postgres: { port, docker: { image } }`) is no longer merged over the preset: it is a custom container, with no `DATABASE_URL` and an `http://` URL. Pass the fields to the helper instead: `postgres: service.postgres({ docker: { image: "postgis/postgis:16" } })`. A key named after a preset with no `docker` is that preset's helper: `postgres: { port }` now gets `pg_isready`, `redis: { port }` `redis-cli`, and `clickhouse` and `mailpit` their secondary port, as `service.<preset>()` does. A key `mysql`, `mongodb` or `postgresql` no longer gets a `mysql://`, `mongodb://` or `postgresql://` URL: give the container a `urlTemplate`. `database`, `user` and `password` on a custom container fail validation; only a preset reads them.
- **Unknown keys fail validation in every section**, not only `typecheck`, `check` and `predeploy`: the top level, each app and service, `options`, `options.hosts`, `options.envFile`, `docker`, `prisma`, `seed` and `secrets`. A misspelt app option (`healthEndpont`) is also a type error in `defineDevConfig`. Delete keys nothing reads.
- **`env.services` and `env.apps` are resolved**: one `kind` each (`container`, `portless`, `job` or `external`; `server`, `worker` or `portOnly`) with every default filled, such as an app's `readiness` and `healthTimeout`. `IntegrationAppContext.config` (`appEnv`, `describeApp`, `bannerHint`) is a `ResolvedApp`. `buildComposeModel`, `computeUrls`, `waitForService` and `waitForAllServices` take resolved services: build them with `resolveServices` (or `resolveConfig`, exported from `buncargo/api`).
- **A `readyWhen` app gets 120 s in CI**, like every other app, instead of 60 s. `waitForServers({ timeout })` and `waitForDevServers`'s `timeout` are gone: each app waits its own `healthTimeout`. `waitForService`'s `maxAttempts` is gone too: set the service's `healthTimeout`. Asking an app already on its port before reusing it waits 3 s, not its `healthTimeout`.
- **A custom container gets a named host only with `exposeProtocol: "http"`.** It was named whenever its key was not a database's. ClickHouse, whose URL carries credentials, is not named.

- **Mailpit containers are recreated once.** `service.mailpit()` now pins `axllent/mailpit:v1.33.1` instead of the untagged image, so a warm start can skip `compose up`. The first run after the upgrade recreates each Mailpit container; its volume and stored mail are kept.
- **A service keyed `minio` with no `docker` is `service.minio()`**, the new MinIO preset, and the apps get `MINIO_URL`.
- **A hyphenated service or app key gets underscored env names.** `my-db` now yields `MY_DB_PORT` and `MY_DB_URL` (was `MY-DB_PORT`, which Compose could not read). Code reading `process.env["MY-DB_PORT"]` reads `MY_DB_PORT`. Two keys with one such name (`my-db` and `my_db`) now fail validation.
- **Apple `container` refuses interpolation it cannot translate.** A service value using `${VAR:+x}` or a default that holds another `${...}` now fails the start with the value named, instead of reaching the container as literal text. Rewrite the value, or use `docker.runtime: "docker"`.
- **Apple `dev --reset` fails when a volume was not removed**, naming each one, instead of warning and reporting success.
- **A `$` in a preset's `password`, `user`, `database` or `apiKey`** now reaches the container as typed. Compose used to interpolate it.
- **Named URLs need a run that serves them.** `getEnvVar`, `env`, `status` and `url` return an app's or service's `https://*.localhost` URL only while a run of the checkout serves it (its route is registered by a live run and, for the CLI commands, the daemon answers for it), and `localhost:<port>` otherwise. They used to return the named URL whenever `options.hosts` was on. Code that needs the plain address whatever runs reads the `*_LOOPBACK_URL` variables or `loopbackUrls`.
- **`DockerUnavailableError` is a `ContainerRuntimeUnavailableError`** (both exported from `buncargo/api`). Code catching `ContainerRuntimeUnavailableError` now catches Docker's too. Its `runtime` is now `"docker"`, as on the base class; read which Docker runs the daemon (`"orbstack"`, `"docker-desktop"`, …) from `dockerRuntime`.
- **`ContainerRuntimeAdapter` (`buncargo/api`) is a narrower port.** An adapter implements `name`, `displayName`, `capabilities`, `availability()`, `ensureRunning`, `containers(signal)`, `logs`, `up`, `down`, `stop(ids)`, `exec`, `execArgv`, `listVolumes`, `removeVolumes`, `listComposeProjectResources` and `removeComposeProjectResource`, and nothing else. `containers` returns every container the runtime holds and throws when the runtime cannot answer: an empty list means it holds none, which the service watch reports as removed. `listVolumes` throws the same way; an adapter that returned `[]` when it could not list now rejects, or the sweep may retire the port claim that names a deleted checkout's volumes. Gone, and derived from that listing by buncargo: `isAvailable` (`availability().state === "up"`), `list`, `projectServiceStates`, `diagnoseService`, `findContainerOnPort`, `containerPortOwners` and `containerPortOwnersAsync`. Renamed: `execInService` is `exec`, `interactiveExecArgv` is `execArgv`, `stopByIds` is `stop` and returns a promise. `probeServicePort` is gone: set `capabilities.hostPortProbe: false` and report each container's `address` and `targetPorts`, and a `tcp` check connects there. `capabilities.jobExitCodes` says whether a `job` can run, `capabilities.composeProjectResources` whether `prune --project` can. `availability()` returns `{ state: "up" }`, `{ state: "down" }` (nothing can be running) or `{ state: "unreachable", detail }`.
- **`listBuncargoContainers` and `stopBuncargoContainers` (`buncargo/api`) return promises**, and so does `explainMissingContainers()` on an environment. Await them.
- **A library `stop()` keeps services another live run uses.** While another live run of the project in the checkout (a `buncargo dev`, another script's `start()`) uses the services, `stop()` stops this environment's apps and releases its claim, leaving the containers up for that run. Pass `stop({ force: true })` to tear them down regardless. `buncargo dev --down` keeps them the same way; `--reset` still removes them.
- **`start()` options:** `skipSeed`, `prefetchSeed` and `skipEnvironmentLog` are gone. Use `seed: "skip"` for `skipSeed: true`, and `seed: "force"` to run the seed whatever `seed.check` says. The banner prints whenever `verbose` is on. New: `claim: { idleTimeoutMs }` (the hold `claimRun()` sets) and `schema: "push"`.
- **`env.restart()` is gone.** It brought the whole config up again whatever the last start selected. Call `stop()`, then `start()` with the options you want.
- **`recordCapture`, `renderGeneratedFiles`, `runServerHook` and `reportServiceChanges` are gone from `DevEnvironment`.** `start()` and `startServers()` record captures, re-render generated files, run the server hooks and report service changes themselves; `buncargo generate` renders the files.
- **`seed`, `setupChecks`, `preflight`, `tasks`, `setNamedHostsActive`, `composeModel` and `ensureComposeFile` are gone from `DevEnvironment`.** They are what `buncargo dev`, `buncargo run` and `buncargo prisma` read; a script reads the same values from its own `dev.config.ts`, and `start()` renders the compose file, switches named hosts and seeds itself.
- **`DevServerPids` is keyed by app** (`DevServerPids<TApps>`): `start()` and `startServers()` resolve to `{ web?: number }`, so `pids.typo` is a type error and `pids.web` is `number | undefined`.
- **`buncargo ci --schema=push` runs the hooks and the other migrations.** The push now takes the place of `prisma migrate deploy` inside the preparation: `beforeMigrations`, the `migrations` entries and `afterContainersReady` run as they do with `--migrate`, and a failed push exits 1 rather than with Prisma's code.
- **Named hosts speak a protocol, and `buncargo hosts install` replaces the daemon once.** The daemon reports a `protocol` number in its health body, and `~/.buncargo/hosts-service.json` (now format 2) records it with the buncargo version. A daemon is stale only below the protocol a project needs, never for being another release, and `buncargo hosts install` keeps a newer daemon unless given `--force`. A daemon installed by 15.x reports no protocol: the first `buncargo dev` after the upgrade prompts to update it (without a TTY it runs on `localhost:port` and says to run `buncargo hosts install`). Upgrade every project on the machine together: a 15.x project still calls the new daemon stale and offers to downgrade it.
- **`BUNCARGO_HOSTS_PORT` is gone.** The daemon binds `:443` (and `:80` for the redirect) only, and apps no longer receive `BUNCARGO_HOSTS_PORT`; it was always `443` outside tests. `~/.buncargo/hosts-daemon.json` is no longer written or read and can be deleted.
- **`unsetEnv` belongs to its environment.** Each environment removes its own config's `unsetEnv` from the processes it starts; the last config loaded no longer applies it to every process buncargo starts. A tool buncargo runs outside an environment (`buncargo slot`, the Shopify and Supabase CLIs, `check`, `predeploy`) keeps those variables.
- **`.buncargo/ports.json` is gone.** A checkout's port block is recorded only by its claim in `~/.buncargo/offsets.json`, which buncargo already kept; no run reads or writes the file any more, and a hand-written `{ "offset": n }` no longer pins a checkout. Use `bunx buncargo ports pin <offset>`, or `BUNCARGO_PORT_OFFSET`. Delete the file from checkouts and `.gitignore` entries that mention it. Read ports from `bunx buncargo env --get ports.<name>`.
- **`portOffsetProvenance` reads `claim` instead of `lockfile`** (`status --json`, `env`, `DevEnvironment.portOffsetProvenance`, the `PortOffsetProvenance` type) when the offset came from the checkout's own claim.
- **A port claim without `ports` or `usedAt` is no claim.** Every claim buncargo 15 writes has both. A checkout whose claim an older buncargo wrote gets a block again on its next run, which may move its ports once.
- **A throwaway run's teardown keeps its claim.** A suffixed environment (E2E, `withSuffix`) or any run in CI gives up its port block when torn down, and the claim stays to record which checkout its volumes belong to; the sweep retires it once no container, run or volume of its project is left. So `buncargo prune`, and the sweep under `BUNCARGO_PRUNE_DELETED_CHECKOUTS=1`, now also find a deleted checkout's E2E volumes. Without the opt-in the sweep keeps a deleted checkout's claim while its project still has volumes, instead of dropping it, so `prune` can propose them.
- **Every command rejects what it does not take.** An unknown flag, a value on a flag that takes none, a flag that needs a value given without one, a flag given twice, a positional too many and arguments after `--` that a command does not use now exit 1 naming them; they used to be ignored. That covers `ls`, `status`, `runs`, `doctor` and `env`, which read no arguments before: `status --jsno` and `env --json` exit 1 (`env` prints JSON without a flag). A value starting with `-` needs `=` (`--command=-1`). `-h` and `--help` print the command's help on every command instead of running it: `doctor --help` ran the sweep and `dev -h` started the environment.
- **`dev <app>...` starts those apps** and their `requiredApps`, as `--apps` does; it used to start every app. `build <app>...` builds those. Naming apps both ways, or with `--profile`, exits 1.
- **An optional flag value is read only after `=`.** `dev --expose api` exposes every `expose: true` target and starts only `api`; write `dev --expose=api`. `typecheck --changed main` exits 1; write `--changed=main`.
- **Subcommands take their own flags and print their own help:** `files`, `secrets`, `ports`, `hosts`, `bar`, `connect`, `env set`/`unset` and `check docs`. A flag of one subcommand on another exits 1 (`files pull --json`, `ports --root`), as does an unknown subcommand (`hosts nope`). `secrets` with no subcommand exits 1, as before.
- **The root help lists each command's own usage**, built from its spec. Its extra rows for single flags (`env --get`, `doctor --fix`, `typecheck --only`) are gone: `buncargo <command> --help` lists them, with the command's exit codes. `buncargo help agents exits` lists every command's exit codes beyond 0 and 1, and its JSON documents.
- **`buncargo restart` answers with what the run did.** It exits 0 once the app's process is replaced, 1 when the replacement failed or the run did not answer (it exited 0 with a warning), 2 when no run of the checkout started the app (was 1), and 3 when the run refused: a script's `start()`, as before, or an app the run reused from another terminal (was 0). The request carries an id the run answers to, so a 15.x `buncargo dev` never answers a 16.0 `restart`: restart such runs after upgrading.
- **`buncargo stop` exits 1 when it could not stop something:** a teardown that failed, a container runtime that refused this user or did not answer, a port it could not free. It exited 3, which now means only that it left something running on purpose (a confirmation or `--force` is needed, or the process could not be identified), so BuncargoBar offers `--force` only where forcing helps.
- **`dev --detach --json`** prints the outcome as one `DetachedResultJson` document, with `hostsWarnings` when named URLs fell back to `localhost:port`. The background run now reports those warnings itself instead of the parent finding them in its log, so `dev --detach` repeats them only from a 16.0 run.
- **`runs.json` is version 2.** Each entry records `lifecycle` (`{ state: "live" }`, or `{ state: "released" | "lost", at }`) and `hold` (`{ kind: "checkout" }` or `{ kind: "timed", ms, inherited }`) in place of `releasedAt`, `ownerLostAt`, `idleTimeoutMs` and `inheritedIdleTimeoutMs`. `buncargo runs --json` prints `version: 2` with entries of that shape. A script reading the file or `runs --json` checks `lifecycle.state === "released"` where it checked `releasedAt`.
- **Integration fields on an app's entry sit under the integration's name.** What `describeApp` returns is recorded as `integrations.<name>` on the app's row (the Expo app's `expo` field is now `integrations.expo`), so an integration can no longer overwrite `url`, `pid` or `status`. An integration's `describeApp` returns its own fields, without wrapping them in its name.
- **Upgrading with a `runs.json` v1 on the machine.** 16.0 reads it as empty, and the first 16.0 run or command that writes replaces it, keeping the old bytes in `~/.buncargo/runs.json.recovery-*`. Stacks that only a v1 entry named are kept while they run and their checkout exists (their port claim still names them); take one down with `buncargo dev --down` in its checkout. A 15.x run still going at that point keeps serving, but its own writes fail from then on, so it never records its release, and a 15.x `stop`, `ls` or BuncargoBar refuses the newer file. Stop 15.x runs before upgrading, and upgrade every project on a machine together.
- **BuncargoBar reads `runs.json` v2 only.** `buncargo dev` offers the update, and `buncargo bar update` installs it; an older app says it is out of date and shows nothing.
- **Service ports listen on `127.0.0.1` only.** They were published on every interface, so another machine on the network reached each database and Redis with their default credentials. A database you open from another machine (a phone, a second computer, a teammate's client) needs `bind: "0.0.0.0"` on that service: `db: service.postgres({ bind: "0.0.0.0" })`, or `bind: "0.0.0.0"` next to `port` on a custom container. Each service's container is recreated once on the first run after the upgrade; its volume and data are kept. Ports listed in a raw `docker.ports` are published as written.
- **`predeploy` seeds only when `predeploy.seed` is set.** It used to run the dev `seed.command` in every named environment outside production, which can create accounts with known passwords in a deployed database. Set `predeploy.seed: true` to keep running `seed.command`, or give it the deploy's own command. `predeploy.seed: false` is gone: delete it, not seeding is the default.
- **Removed from `buncargo/api`:** `getDevEnv()` (keep the environment `loadDevEnv()` returns), `sleep` (use `Bun.sleep`), `logFrontendPort` and `logApiUrl` (print the line yourself), and `getEnvVar`'s third argument, `{ log }`: `getEnvVar(config, "VITE_PORT")` no longer prints `using_frontend_port:<port>`. Removed from `DevEnvironment`: the synchronous `prepareStart` (await `prepareStartAsync`) and `stopProcess` (`process.kill(pid)`, or `stop()`).
- **buncargo does not run on Windows.** It stops at once and says to run it in WSL; the Windows downloads of `cloudflared` and `mkcert` are gone.
- **One events log, `~/.buncargo/events.json`.** The removal log and the record of detached runs the watchdog stopped are one file, each event with a `kind` (`containers`, `volumes`, `services`, `run-stopped`). `removals.json` and `run-stops.json` are no longer read; delete them. `status --json` `recentStops` entries carry `kind`.
- **No option of the programmatic API relocates or speeds up buncargo for a test.** `startPublicTunnels` (`buncargo/api`) takes only `signal` and opens Cloudflare quick tunnels; its `start` option, and the `url`, `publicUrl`, `tunnelUrl`, `stop` and `destroy` shapes it accepted from one, are gone. Point `BUNCARGO_CLOUDFLARED_PATH` at another `cloudflared` instead. `waitForService` and `waitForAllServices` no longer take `pollInterval`. To keep a test off `~/.buncargo`, point `HOME` at a temporary directory.
- **`readOnly` is gone** from `loadDevEnv` and `createDevEnvironment`. Nothing read it: loading never probed or claimed a port block either way. Delete the option. Loads that differed only by it now share one cached environment.

## 14.0 → 15.0

- **Bun 1.4.4 or newer is required** (`engines.bun`, previously `>=1.4.2`). Upgrade with `bun upgrade`, and update any `.bun-version`, `packageManager` or CI `bun-version` pin that names an older release. `check.format` already needed it, because older Bun has no `bun fmt`.

## 13.0 → 14.0

- **A run refuses a Compose project name another checkout uses.** `dev`, `ci` and `start()` used to share the other checkout's containers and database silently; they now stop with an error naming both checkouts. Self-hosted CI runners whose checkouts share a directory name, which used to start on separate ports under one project, need a `projectPrefix` that differs per runner, and a `dev.config.ts` below a worktree's top level needs one that differs per worktree; [Ports and isolation](./reference.md#ports-and-isolation) shows both. Start the checkout once after changing it so its claim records the new name.
- **A named-hosts daemon from before 12.0 is no longer used.** One that answers without reporting the hostnames it serves now leaves the run on `localhost:port` with "Run `buncargo hosts install` to update it", and `doctor` and `hosts status` report it as outdated. Run `buncargo hosts install` once on each machine that still has one.
- **`buncargo send` exits by what became of the keys.** It waits for the run to answer: `0` typed, `2` no run started that app (was `1`), `3` the app cannot take keys because it has no terminal of its own or is not running (was `0`, with only a warning in the run's output), `1` when the run does not answer within 5 seconds. A script that ignored `send`'s exit code should check for `3`.
- **`stop({ removeVolumes: true })` fails when it keeps the volumes.** The generated compose file was looked up from the process's working directory instead of the checkout, so a caller running from elsewhere (an E2E runner in `apps/web`, a CI step with `working-directory`) removed the containers and kept every volume, with only a warning. The file is now found from the checkout. When it really is missing (Docker), the volumes are found by Compose's `com.docker.compose.project` label and removed; `stop()`, `dev --reset` and `ci`'s teardown throw only for a volume Docker would not remove, naming it. A workflow step that ran `docker volume rm` after a reset can go. If your teardown kept its volumes before, it now removes them as asked.
- **`buncargo sim` is gone.** Use `buncargo expo sim`, which takes the same arguments. BuncargoBar runs `expo sim` from this release on, which every buncargo since 10.2 answers.
- **Removed exports:** `isDockerRunning` (use `isDockerDaemonRunning` from `buncargo/docker`), `isPortAvailable` (use `isPortInUse` from `buncargo/core/process`), `stopAllProcesses` from `buncargo/core/process` (call `stopProcess` per pid), `waitForServiceByType` (use `waitForService`), `MAX_ATTEMPTS` and `POLL_INTERVAL` from `buncargo/container-runtime` (a service's `healthTimeout` sets how long readiness waits), `DOCKER_NOT_RUNNING_MESSAGE` from `buncargo/docker` (match `DockerUnavailableError` instead of the message), `ExpoIntegration.appOptions()`, and `readBuncargoViteEnvironment`, `resolveBuncargoViteProxy`, `buildBuncargoViteConfig`, `defaultBuncargoViteHost` and `BuncargoViteEnvironment` from `buncargo/vite` (use the `buncargoVite` plugin). `buncargo/cli` now exports only `runCli` and `CliOptions`; `selectProfileApps`, `getFlagValue`, `hasFlag` and `splitCliArgs` are gone from it.
- **`DevEnvironment.workspaceId`, `prepareStart` and `prepareStartAsync` are required.** `createDevEnvironment` always set them, so drop the `?.` when calling them; an object you build to stand in for a `DevEnvironment` must now provide all three.
- **The sweep and `dev --down --all` remove only stacks your own `~/.buncargo` names.** A stack with no entry in `runs.json` and no port claim in `offsets.json` for its project and checkout (another user's on a shared Docker daemon, or one whose state was wiped) is no longer removed, even when it is stopped or its checkout is gone. `ls`, `doctor` and `dev --down --all` list each one with the command that removes it by hand. `decideSweep` takes a required `known` and answers `{ kind: "foreign" }` for such a stack, and `SweepResult` lists them in `foreign`.
- **`decideSweep` takes `checkout: "present" | "deleted" | "unknown"`** in place of `rootExists: boolean` (`buncargo/container-runtime`). Pass `"deleted"` only for a checkout confirmed missing; one you cannot read is `"unknown"`, which counts as present.
- **A library `start()` takes `exclusive` leases.** It used to start an exclusive app while another run held its lease. Now, while a `buncargo dev` or another `start()` holds it, an `essential: false` app is left out with a warning and an essential one makes `start()` throw, naming the holder and `buncargo stop --all --root <checkout>`. A script or test that starts an exclusive app while a `dev` runs it stops that run first, or leaves the app out with `onlyApps`.
- **A library `start()` without containers is a run in `~/.buncargo/runs.json`.** Its apps show in `buncargo ls` and BuncargoBar, and it starts the watchdog once they are up. A test that starts one from a temporary `HOME` passes `start({ watchdog: false })`, as it already must for a start with containers: a watchdog started there outlives the test.
- **Removed fields nothing read:** `binary` on `ComposeCommandContext`, `isCI` on `startDevServers` options, `composeFile` on `ExecInServiceRequest` and `HealthCheckContext`, `projectId` and the pooler, analytics and edge runtime `enabled` flags on `SupabaseProject`, and `wait` on `ContainerUpRequest`: a custom container runtime adapter starts containers without waiting for them, and buncargo polls readiness itself.

## 12.0 → 13.0

- **`dev` opens the terminal UI whenever it runs in a terminal.** `--tui` is no longer needed; pass `--no-tui` for prefixed lines. Runs without a terminal (CI, agents, piped output, `--detach`) still print prefixed lines.
- **`interactive: true` takes effect only with `--no-tui`.** In the TUI every app has a terminal of its own, so an Expo app's keys work in its pane. A script that relies on an app owning the real TTY should pass `--no-tui`.

## 11.0 → 12.0

12.0 is a hard cutover: the compatibility code for older versions, configs and on-disk state is gone. **Stop every run before upgrading** (`bunx buncargo dev --down --all` with the old version): 12.0 does not recognise an older run's containers or locks.

- **Worktree project names stop repeating the worktree.** A worktree in a directory named after it (`t3code-fc4fa622`) was `gey-t3code-fc4fa622-t3code-fc4fa622` and is now `gey-t3code-fc4fa622`; its E2E stack `gey-t3code-fc4fa622-e2e`. The volumes are named after the project, so each such worktree starts on an empty database: seed again, and `bunx buncargo prune` removes the old volumes. Anything that names containers by hand needs the new name; `buncargo sql` and `buncargo status --json` find them for you.
- **Offsets are claimed per checkout** in `~/.buncargo/offsets.json`. A worktree that shared its hashed offset with another may move once to the next free block, and then keeps it.
- **`options.hosts.primaryApp` is gone.** Set `options.primaryApp` instead; it also gives that app the bare named hostname.
- **`options.frontendApp`, `options.expoApiApp`, `getFrontendPort()` and `getExpoApiUrl()` are gone**, and so is `expo({ apiApp })`. Read ports and URLs from `env.ports` / `env.urls`, or `buncargo env --get`.
- **Expo needs `integrations: [expo()]`.** The per-app `expo` field is gone, and an app whose `devCommand` runs `expo` is no longer made an Expo app without the integration.
- **Removed names:** the `dev-tools` binary (use `buncargo`), the `dev-tools.config.ts` / `.js` config file names (use `dev.config.ts`), and `BUCARGO_SKIP_MKCERT` (use `BUNCARGO_HOSTS=0`).
- **Removed exports:** `spawnDevServer` (use `startDevServers`), the sync `buildApps` from `buncargo/core/process` (`buildApps` is now the async one), `logExpoApiUrl`, and the `mergeConfigs` overload taking explicit type parameters.
- **Custom container runtime adapters** must implement `containerPortOwnersAsync`, and an injected Apple CLI must implement `runAsync`.
- **Older on-disk state is not read.** Process identities without the `v2:` prefix no longer match (an older run reads as gone), the old `.lock` file protocol is ignored, and `mkcert` / `cloudflared` cached under `tmpdir()` are downloaded again into `~/.buncargo/bin`.
- **BuncargoBar installs need the release's checksum**, which every release publishes.
- **Removed config errors:** a top-level `envVars` or an app-level `env` is no longer explained by a dedicated error; use the top-level `env` overlay and `apps.<name>.staticEnv` / `envVars`.

## 10.0 → 11.0

11.0 added the terminal UI (`dev --tui`) and supervision for apps that may stop without ending the run.

- **`interactive: true` only applies in stream mode.** The TUI gives every app a terminal of its own, so it ignores the setting. Stream mode (the default, and every run without a terminal) still hands that app the TTY. `--attach=<app>` does the same for one run.
- **The Shopify CLI app is non-essential and not interactive.** Its exit no longer ends the run: it shows as stopped, and `r` in the TUI or `buncargo restart shopify` starts it again. Its `p`/`g` keys open the preview and GraphiQL URLs. Remove any `interactive: true` you added to it.
- **App output is logged.** Every run writes `.buncargo/logs/<run>/<app>.log` (the last ten runs). Keep `.buncargo/` in `.gitignore`; `buncargo setup` adds it.

## 9.0 → 10.0

Container cleanup now runs from one machine-wide sweep against one run registry (`~/.buncargo/runs.json`). It used to rely on a watchdog per project that tracked heartbeat files.

- **Upgrade every project on the machine together.** New runs record process identities in a `v2:` format that 9.x cannot read. When a 9.x CLI writes the registry, it drops every entry from the new version, including live runs, so those runs vanish from `buncargo runs` and the menu bar and lose their idle hold. Their running containers are left alone, and volumes are never touched.
- **Library `start()` now claims its run and starts the watchdog.** A `dev.start()` from a script shows up in `runs`, `stop` and the menu bar. Its containers stay up after the script exits, as long as the checkout exists, unless you request a hold with `claimRun({ idleTimeoutMs })` before `start()`. `options.autoShutdown` and the three-minute default apply to `buncargo dev` only. To skip starting the watchdog process, pass `start({ watchdog: false })`. The claim is made either way.
- **`DevEnvironment` API changed.** `startHeartbeat`, `stopHeartbeat`, `spawnWatchdog` and `stopWatchdog` are replaced by `claimRun`, `releaseRun`, `ensureWatchdog` and `sessionId`. The unread `autoShutdown` property is gone.
- **Removed exports.** The root package no longer exports `areContainersRunning`, `isContainerRunning`, `getHeartbeatFile`, `isWatchdogRunning`, `spawnWatchdog`, `startHeartbeat`, `stopHeartbeat` or `stopWatchdog`. `buncargo/docker` no longer exports `areServicesRunning`, `areContainersRunning`, `isContainerRunning` or `startService`. Use `ensureWatchdog` in place of the watchdog functions. `getWatchdogLogFile()` now takes no arguments, and the log lives in `~/.buncargo/watchdog.log` instead of `/tmp`.
- **Custom container runtime adapters.** `ContainerRuntimeAdapter` is async-only and gains `listVolumes` and `removeVolumes`. `BuncargoContainer` gains a required `state`.
- **Teardown removes containers instead of stopping them.** `dev --down --all` and stopping a whole run now bring the containers down. A stack whose checkout was deleted, or which is stopped with no owner, is removed by the sweep.
- **Containers from one-shot modes are kept longer.** `--keep-containers`, `autoShutdown: false` and the one-shot modes (`--up-only`, `--migrate`, `--seed`) set no idle hold. Their containers now live as long as the checkout, even if the run crashed.
- **Infisical defaults to the EU cloud.** `siteUrl` now defaults to `https://eu.infisical.com`, the same as `hanzio/secrets`. A project on the US cloud sets `secrets: { siteUrl: "https://app.infisical.com" }`. Secrets are now read the way hanzio reads them, as a CLI session token and then HTTP, instead of `infisical export`. The CLI must support `infisical user get token`.
- **Secrets reach commands, not only apps.** With a config-level `secrets` scope, migrations, the seed, `exec`, `prisma` and hooks' `ctx.exec` now get its values, beneath the computed env. Use `secrets: false` on an app, migration, the seed or an `exec` call to opt out. Config-level `secrets: false` disables all buncargo requests, including startup prefetch and explicit child scopes, for an offline environment. Apps now receive the same per-scope injection with machine credentials as with a CLI login. Secrets copied into `.env` for these can go.
- **Expo is an integration.** Add `integrations: [expo()]` from `buncargo/expo`. The per-app `expo` field, `options.expoApiApp`, and inferring Expo from a `devCommand` still work, with a warning, until the major after this one.
- **Volumes are never removed automatically.** To clear old worktree databases, run `bunx buncargo prune --dry-run`, then `bunx buncargo prune`.

## 8.0 → 9.0

- **Tailscale sharing is gone.** It arrived in 8.2.0 and was removed in 9.0. Remote sharing now runs over frp. The `buncargo tailnet` command and `TS_AUTHKEY` enrollment are removed, and nothing in 9.x cleans up an installed tailnet coordinator. Run `bunx buncargo tailnet uninstall` on 8.2.x before you upgrade.
- **Recipient tokens are new.** Get a token with `bunx buncargo connect token` or from BuncargoBar, and set it as `BUNCARGO_CONNECT_TOKENS`. Use comma-separated `bc_share_…` tokens (up to 16) instead of 8.0's `bc1.…` tokens or JSON array. `BUNCARGO_CONNECT_NAME` groups runs in the menu bar.
- **Sharing no longer filters on `expose`.** With tokens set, every selected app and service that has a host port is shared, and workers, jobs and portless targets are skipped. `expose: true` now only controls public `--expose` quick tunnels.

## 7.0 → 8.0

- **Tailscale removed.** The first Tailscale integration (7.7 to 7.10) is removed. That covers the `buncargo tailnet` commands, the `--tailnet` / `--no-tailnet` flags, `BUNCARGO_TAILSCALE_PATH`, and `tailnetUrls` / `setTailnetUrls` on `DevEnvironment`. Run `bunx buncargo tailnet uninstall` on 7.x first, because 8.0 does not remove the coordinator. Private sharing moved to `BUNCARGO_CONNECT_TOKENS` together with `expose: true` and the new optional `exposeProtocol: "http" | "tcp"`.

The following breaking changes shipped in 7.6.0 and were never marked as such, so you meet them on this jump:

- **Bun 1.4.2 or newer is required** (`engines.bun`, previously `>=1.0.0`). Stop running dev sessions and rerun `bunx buncargo hosts install` after upgrading, because the file-lock protocol changed and old and new processes cannot share it.
- **One-shot modes do less.** `dev --up-only` now starts containers and syncs dotenv only: no migrations, generation or seed. `--migrate` does not generate or seed. You can pass only one of `--migrate`, `--seed`, `--up-only`, `--down` and `--reset`, and `--all` requires `--down`.
- **A 404 no longer counts as healthy.** A configured `healthEndpoint` must return a success status. Point it at a real route, or set `healthEndpoint: false`.
- **Server hooks run only when servers start.** `beforeServers` and `afterServers` no longer run on preparation-only calls.
- **`docker.writeStrategy: "if-missing"` is stricter.** It now refuses an existing compose file that differs from the model. Move hand-written YAML into `service.docker` and use `"always"`.
- **The config typecheck needs a local TypeScript.** It uses the project's installed `tsc` and errors if there is none, where it used to fall back to `bunx tsc`.

## 6.0 → 7.0

- **Reinstall the named-hosts service.** The daemon now runs a bundled `hostsd` file installed under `/usr/local/libexec/buncargo`, not the CLI in `node_modules`. Run `bunx buncargo hosts install` once, and `hosts status` / `doctor` will report a stale service until you do.
- **`buncargo typecheck` behaves differently.** It runs workspaces in parallel, with concurrency set by CPU count and capped at 4 locally and 2 in CI. It also typechecks the root `dev.config.ts`, which can surface new errors. Use `--concurrency=N` or `BUNCARGO_TYPECHECK_CONCURRENCY` to throttle, and `--only=<workspace>` to narrow it. Add `.buncargo/` to `.gitignore`.

## 5.0 → 6.0

Types only. Runtime config is unchanged, but code that relied on loose types stops compiling.

- **`ComputedEnvVars` lost its open index signature.** Reading an unknown key from `buildEnvVars()` / `buildAppEnvVars()` is now a compile error. Declare the key in the top-level `env` return value or the app's `envVars` / `staticEnv`.
- **`getEnvVar` returns the overlay's declared type.** For example, it returns `number` for a `number` value, not `string | number | undefined`.
- **Option keys must name configured keys.** `options.primaryApp`, `expoApiApp`, `frontendApp`, `hosts.primaryApp`, `hosts.services`, `prisma.service` and `prisma.urlEnvVar` are typed to the config's own service, app and env names.
- **`DevConfig` and related types gained type parameters.** This includes `TEnv` on `DevConfig`, and generics on `DevOptions`, `HostsOptions`, `PrismaConfig` and `StartOptions`. Explicit annotations using these types may need updating. Prefer `typeof config` with `DevEnvironmentFor`.
- **`undefined` values are omitted.** An `env` or `envVars` value of `undefined` is left out instead of becoming the string `"undefined"`.

## 4.0 → 5.0

No consumer-facing changes: 5.0.0 is the 4.0.0 code with a new version number. 4.0.0 was never published to npm, so 3.2.5 → 5.0.0 is the real upgrade path. Follow the section below.

## 3.0 → 4.0

**Config renames.** Validation rejects the old keys with a message naming the new ones.

- Top-level `envVars` becomes `env`, with the same `(ports, urls, ctx) => ({ … })` callback. It is now an overlay on the computed values for every process, and service presets already inject `DATABASE_URL`, `REDIS_URL` and similar values.
- `apps.<name>.env` becomes `apps.<name>.staticEnv`, with the same constant map. Computed per-app values go in the new `apps.<name>.envVars`.

```ts
// before (3.x)
envVars: (ports, urls, { publicUrls }) => ({ WEB_URL: publicUrls.web ?? urls.web }),
apps: { api: { port: 3000, devCommand: "bun dev", env: { LOG_LEVEL: "debug" } } },

// after
env: (ports, urls, { publicUrls }) => ({ WEB_URL: publicUrls.web ?? urls.web }),
apps: { api: { port: 3000, devCommand: "bun dev", staticEnv: { LOG_LEVEL: "debug" } } },
```

Leave `services.<name>.env` alone: in 4.0 it is a new, different field, a map of env names to `"url" | "port" | "secondaryPort"`.

**Behavior changes.**

- **Ports move.** Every checkout, including the main one, gets a hashed offset between 100 and 9000 in steps of 100, persisted in `.buncargo/ports.json`. Postgres is no longer on `5432`. Read ports from `bunx buncargo env --get ports.<name>` or the injected env, or pin them with `BUNCARGO_PORT_OFFSET`.
- **`devCommand` runs through a shell.** It used to be split on spaces, so inline env prefixes and quoting now work. `devCommand: false` reserves a port without starting a process.
- **Running apps are reused.** An app already listening on its port is reused instead of killed.
- **Unknown CLI flags are rejected.**
- **Migrations run in order.** Configured `migrations` run one after another instead of in parallel.
- **Seeding is stricter.** A failed seed fails `start()`, where it used to log and continue. `dev --seed` without a `seed` block is now an error instead of running `bun run run:seeder`.
- **The idle timeout is shorter.** `buncargo dev` now tears containers down after 3 minutes, down from 10 (`options.autoShutdown`, `--watchdog-timeout`, `--keep-containers`).
- **Preset and option validation is stricter.** The `redis` preset no longer accepts `database`, `user` or `password`; use `service.custom()` if you need them. On a preset, `healthCheck: "tcp"` now emits no container healthcheck. `expoApiApp`, `frontendApp`, `hosts.primaryApp` and `prisma.service` must name configured keys.

**Type and API changes.**

- **`publicUrls` is narrower.** It is typed only with keys marked `expose: true`, so reading a key that is not exposed is a compile error.
- **Removed from the root export:** `getFlagValue`, `hasFlag`, `calculatePortOffset`, `killProcessOnPort`, `killProcessOnPortAndWait`, `killProcessesOnAppPorts` (use `killPortOwner`), `DOCKER_NOT_RUNNING_MESSAGE`, `MAX_ATTEMPTS` and `POLL_INTERVAL`. `isCI` is still exported.
- **Removed options:** `StartOptions.suffix`, `CliOptions.watchdogTimeout` and `CliOptions.devServersCommand`. `buncargo/core/process` is now a directory module; the import path is unchanged.
